# QURAL-SAIMAN — статус проекта

CRM для аренды строительного инструмента. Казахстан, Атырау. Валюта — тенге (₸).
Развёрнут на Railway, автодеплой из GitHub.

**Как использовать:** прочитайте этот файл первым в новой сессии — здесь всё текущее
состояние, архитектурные решения и грабли, на которые уже наступали.

---

## 1. Стек

- **Next.js 15.5** (App Router) + React 19 + TypeScript + Tailwind CSS 4
- **SQLite** через `better-sqlite3` — `data/app.db` локально, `/data/app.db` на Railway
- **REST API** — Next.js route handlers (`src/app/api/**`)
- **Zustand** (`src/lib/store.ts`) — клиентский кэш поверх API, НЕ источник истины
- **iron-session** + **bcryptjs** — авторизация и хеширование паролей
- **TipTap** — WYSIWYG-редактор шаблонов документов
- **Recharts** — графики в Аналитике и Финансах
- **mammoth** — импорт Word (.docx) в редактор шаблонов
- **qrcode** — QR-коды инвентаря, **xlsx** — импорт/экспорт клиентов

**Дизайн — «тёплый минимал»** (тема переделана, тёмная панель и фиолетовый акцент убраны):

| Роль | Значение | CSS-переменная |
|---|---|---|
| Фон страницы | `#FAF9F6` тёплый белый | `--color-bg` |
| Меню | `#F2F0EA` тёплый песок | `--color-sidebar` |
| Текст меню / приглушённый | `#1A1A17` / `#6E6C63` | `--color-sidebar-text`, `--color-sidebar-muted` |
| Граница меню | `#E2DED2` | `--color-sidebar-border` |
| Акцент | `#0E7C66` изумруд | `--color-primary` |
| Акцент наведение / подложка | `#0B6352` / `#E2F1EC` | `--color-primary-hover`, `--color-primary-soft` |
| Границы | `#E6E2D8` | `--color-border` |
| Текст / приглушённый | `#1A1A17` / `#6E6C63` | `--color-text`, `--color-text-muted` |

Скругления 12–16px, мягкие тени. Тень акцентных кнопок вынесена в `--shadow-primary`.

**Шрифт — Onest** (один на весь интерфейс, у него хорошая кириллица), заголовкам задан
трекинг `-0.015em`. Manrope и Inter больше не подключаются.

**Тёмная тема.** Переключатель в «Настройки → Оформление»: Светлая / Тёмная / Как в системе.
Выбор хранится в `localStorage` под ключом `qs-theme` — это настройка браузера, а не аккаунта,
у разных пользователей она своя.

- `src/components/layout/theme-provider.tsx` — контекст `useTheme()`, ставит на `<html>`
  атрибут `data-theme="light|dark"` и следит за системной темой в режиме «как в системе»
- В `layout.tsx` есть **блокирующий скрипт** `themeBootstrap`, который выставляет атрибут
  до первой отрисовки. Без него страница мигает светлым, пока не смонтируется провайдер
- Тёмная палитра: фон `#0A0A0B`, поверхности `#141417`, меню `#101012`,
  акцент `#17B892` (мята), текст на акценте `#04211B`

**`--color-on-primary`** — текст и иконки поверх акцентной заливки. В светлой теме белый,
в тёмной почти чёрный: на мятной кнопке белый текст нечитаем. Все кнопки с
`bg-[var(--color-primary)]` используют этот токен, а не `text-white`.

**Слой перекраски статусов** в конце `globals.css`. Статусные цвета (пастель + насыщенный
текст) зашиты в классы Tailwind примерно в 250 местах по проекту. Вместо их переписывания
в тёмной теме переопределяются конкретные утилиты:

```css
:root[data-theme="dark"] .bg-[#EAF7EE] { background-color: var(--tone-green-bg); }
```

Обратные слэши обязательны — Tailwind экранирует `[`, `#` и `]` в имени класса.
Без них правило невалидно и браузер молча его выбрасывает. Добавляете новый пастельный
цвет — добавьте и правило сюда, иначе в тёмной теме он останется светлым пятном.

**Правила по цвету:**
- Новые элементы красить только через переменные, хардкод hex акцента не заводить
- Статус аренды «Забронировано» переведён с фиолетового на синий `#2B5FD9` — изумруд
  занят акцентом, а зелёный «Завершено»
- Меню светлое: белого текста в `sidebar.tsx` и `mobile-topbar.tsx` не должно быть,
  кроме как на акцентной заливке — там `text-[var(--color-on-primary)]`
- Поверхности красить `bg-[var(--color-surface)]`, а не `bg-white` — иначе карточка
  останется белой в тёмной теме

## 2. Авторизация и права (RBAC)

### Вход
- Страница `/login`, тёмная, логотип QURAL-SAIMAN
- Главный администратор создаётся автоматически: **логин `admin`, пароль `admin`**
- Сессия — cookie `rental_crm_session` через iron-session, 7 дней

```
dashboard.view

workshop.view / workshop.edit
documents.view / documents.edit
blacklist.view
analytics.view
```

- Пункты меню в сайдбаре скрываются если нет права
- Проверка на уровне API через `requireAuth("permission")` в `src/lib/auth.ts`

### Страница `/users`
Создание, редактирование, блокировка, удаление. Права чекбоксами по группам +
кнопки «Выбрать все» / «Снять все».

**Безопасность:**
- Администратора нельзя удалить или заблокировать
- Администратор меняет только СВОЙ пароль (кнопка 🔑 видна только в своей строке)

## 3. Что полностью работает

### Аренды (`/rentals`)

**Нумерация сквозная, по порядку создания** (№1, №2, №3…). Номер присваивает **сервер**
в `createRental`, значение из тела запроса игнорируется — на клиенте два менеджера
могли бы одновременно получить одинаковый номер.

Счётчик лежит строкой `rental_counter` в `company_settings` и только растёт:
`MAX(number)` не годится (у аренд, созданных до этого, номер — обрывок метки времени
вроде `806978`), а `COUNT(*)` дал бы дубли после удаления аренды. При первом обращении
счётчик стартует с числа уже существующих аренд.

В базе номер лежит **без решётки**, «№» подставляет интерфейс. У старых записей решётка
срезается при чтении (`rentalRowToDomain`), поэтому вид одинаковый. В шаблонах документов
`{{rental_number}}` тоже без решётки — она уже есть в тексте шаблона (`АКТ №{{rental_number}}`).

Цикл: **запрос → забронировано → в аренде → завершено / просрочено / украдено / отменено**

**Вкладки:** Все / Запрос / Забронировано / В аренде / Завершено / Просрочено /
Должники / Украдено / Отменено / Архив

**Должники** — только `active`/`overdue` + `total > paid` (неоплаченные брони не попадают)

#### Форма новой аренды (`/rentals/new`)
- Поиск клиента или создание нового (модалка с полями документов)
- **Предупреждение о ЧС** — при выборе клиента из чёрного списка открывается блокирующая
  модалка со списком краж (номер, товары, сумма) и просрочек. Кнопки:
  «Да, оформить (беру ответственность)» / «Отмена»
- Пункт проката: **Атырау по умолчанию**, ещё есть Астана
- Товары **только из каталога**, ручной ввод убран
- **Мультивыбор товаров** — чекбоксы, при выборе можно поменять цену за сутки
- **Комплекты и услуги тоже выбираются из каталога** (`add-catalog-bundle-modal.tsx`),
  ручной ввод убран полностью
- Компактные карточки по категориям (Продукты / Комплекты / Услуги)
- Модалка оплаты: тип (Оплата компаний / Наличные / Kaspi QR) + сумма
- Кнопки «Сохранить изменения» (`request`) и «Забронировать аренду →» (`booked`)

#### Карточка аренды (`/rentals/[id]`)
Правая панель `rental-side-panel.tsx` — все действия:

| Действие | Условие | Что делает |
|---|---|---|
| **Выдать в аренду** | `booked` | → `active`, `issuedBy` из сессии. Если не оплачено — предупреждение «попадёт в Должники» |
| **Принять оплату** | остаток > 0 | Модалка: тип оплаты + сумма → `paid`, `paymentStatus` |
| **Скидка** | всегда | Модалка: ₸ или %, предпросмотр итога → уменьшает `total` |
| **Возврат средств** | `paid > 0` | Модалка: сумма → уменьшает `paid` |
| **Возврат товара** | оплачено + `active`/`overdue` | **Мультивыбор** с чекбоксами, у каждого товара состояние: Исправен / Профилактика / Ремонт. Частичный возврат оставляет аренду активной |
| **Украдено** | `active`/`overdue` | Модалка → товары `stolen`, аренда `stolen`, клиент в ЧС |
| **Товар возвращён клиентом** | `stolen` | Модалка: убрать из ЧС или оставить. Товары → `repair`, аренда → `completed` |
| **Залог** | всегда | Модалка: тип (Денежный/Оборудование/Документ) + сумма |
| **Авто-штраф** | всегда | Модалка: переключатель + ставка ₸/час |
| **Ручной штраф** | всегда | Модалка: причина + сумма → прибавляется к `total` |
| **Расходы** | всегда | Модалка: тип + сумма |
| **Заметки** | всегда | Сохраняются в БД, отправка по Enter |

#### История аренды, паузы и откат ошибок

В шапке карточки — кнопка паузы и меню «…»: История аренды · История пауз ·
Отменить аренду · Удалить аренду.

**История аренды** (`rental_events`). Записи делает не интерфейс, а `updateRental`:
он сравнивает аренду до и после изменения и пишет только то, что реально поменялось —
статус, оплата, сумма, состав, даты. Один разбор в репозитории вместо десятка ручных
вызовов по кнопкам, иначе часть действий неизбежно забыли бы залогировать.

**Откат ошибочного действия.** У события хранится `before_json` — значения полей ДО
изменения. Кнопка отмены применяет их обратно (`revertRentalEvent`), помечает событие
`reverted = 1` и **записывает сам факт отката отдельной строкой** — из журнала ничего
не исчезает. Повторно откатить то же событие нельзя (400). Откат идёт через
`updateRental(..., { silent: true })`, иначе он сам породил бы новое событие и история
зациклилась бы.

**Паузы** (`rental_pauses` + колонка `rentals.paused_at`). Пауза — не статус, а флаг:
аренда остаётся «В аренде», рядом появляется бейдж «На паузе».

- на паузе аренда **не просрочивается и не копит штрафы** — планировщик
  `applyOverdueAndPenalties` отбирает записи с `paused_at IS NULL`
- при снятии с паузы **дата возврата сдвигается на время простоя**: иначе клиент,
  у которого работы встали не по его вине, получил бы просрочку
- «История пауз» показывает каждый простой с длительностью и суммарное время

**Удаление аренды** освобождает занятый инвентарь и удаляет её документы, события и паузы.
Колонка `paused_at` добавляется в существующую таблицу через `ensureColumns`.

**Редактирование дат** — кнопка «✏ Изменить даты», два поля `datetime-local`,
продолжительность пересчитывается на лету. Комментарий тоже редактируется.

**Менеджер** — из активной сессии (`useAuth()`), не захардкожен.

### Автоматический пересчёт при просрочке
`applyOverdueAndPenalties()` в конце `src/lib/repo.ts`:
- Аренды `active`/`booked`/`overdue` с `end_at` в прошлом → статус `overdue`
- **Пересчёт `total` по фактическим дням**: взял на 3 дня по 1000₸ (`total=3000`),
  вернул через 5 дней → `total=5000`. Услуги не умножаются на дни.
- Если включён почасовой штраф — пересчёт по дням НЕ применяется (чтобы не дублировать)
- `total` только растёт
- Запуск: раз в час фоном + при GET `/api/rentals/[id]` + вручную `GET /api/cron`

### Каталог (`/catalog`)
Пять вкладок в одной странице: **Продукты · Комплекты · Услуги · Инвентаризация · График занятости**.
Кнопка действия справа от вкладок меняется под активную вкладку, доступна только с правом `catalog.edit`.

#### Продукты
Запись в БД по-прежнему = одна физическая единица (свой артикул, QR, статус, блокировка при аренде).
Вкладка **группирует единицы по названию** и показывает их свёрнутыми — отдельной вкладки
«Инвентари» нет намеренно, единицы раскрываются стрелкой в строке продукта.

- Таблица: Название · Категория · Артикул · Доступность (`2/2 Свободно`) · Неисправно · Цена.
  Артикул группы — общий, если у всех единиц один, иначе диапазон `QS.0001…QS.0003`
- Статистика: Продукт / Кол-во / Свободно / Забронировано / В аренде / Неисправно / На ремонте /
  Списано-украдено. «Забронировано» считается из аренд в статусе `booked`/`request`
- Фильтры: поиск, пункт проката, категория, тип продуктов, «Только свободные», экспорт в Excel
- Кнопка **«Неактивные инвентари»** переключает список на украденные и списанные единицы
- В форме добавления есть поле **«Количество единиц»** — создаёт N записей, каждой свой артикул
- **Артикул присваивается автоматически, если поле оставили пустым** (`nextSku()` продолжает
  существующую нумерацию: `QS.0001, QS.0002…`). Без артикула не построить QR-код, поэтому
  пустым он больше не остаётся

Статусы единицы: `available`, `rented`, `maintenance`, `repair`, `stolen`, `written_off`.

**QR-код** содержит JSON `{id, sku, name, category, url}`. Кнопка «Распечатать QR»
открывает окно с QR + данными товара и вызывает печать.

#### Комплекты (таблица `kits`)
Название, категория, фото, цена за сутки, состав из позиций. Позиция может быть **привязана
к продукту каталога** — тогда доступность комплекта считается как минимум по составу
(`kitAvailability`); если привязок нет, показывается «∞ Свободно».
Статистика: кол-во комплектов, свободно, общая выручка (из аренд по названию).

#### Услуги (таблица `services`)
Название и **тарифы**: День / разовая / за период, у каждого своя цена
(показываются как «День (разовая,за период)» — как в референсе).
Статистика: кол-во услуг, общая выручка, средний чек.

#### Инвентаризация (таблица `inventory_checks`)
Две подвкладки: **Список для проверки** и **История проверок**.
Фильтры по состоянию: Все / Исправен / Сломан / Не проверено (со счётчиками).
Колонки: Инвентарь · Артикул · Статус · Состояние · Проверял · Последняя аренда · Последняя проверка.
Кнопка «Проверить» пишет запись (кто, когда, состояние, комментарий). Если отмечено
**«Сломан» и единица свободна** — она переводится в статус `repair` и перестаёт попадать
в новые аренды (единицы в аренде и украденные не трогаются).

#### График занятости
Диаграмма Ганта: строки — единицы инвентаря, колонки — дни выбранного периода
(по умолчанию текущий месяц, максимум 190 дней). Полосы аренд кликабельны и ведут на карточку,
цвет — по статусу аренды, сегодняшний день подсвечен. Фильтры: поиск, период, категория,
пункт проката. Легенда Исправен / Сломан.

### Клиенты (`/clients`)
CRUD, поиск/фильтры, сортировка, статистика, импорт/экспорт CSV и Excel.
Бейдж «В чёрном списке» в шапке карточки.

**Блок «Документ клиента» зависит от типа клиента** — и в форме `/clients/new`, и в быстрой
модалке из формы аренды:

| Физ. лицо | Юр. лицо |
|---|---|
| ИИН, дата рождения, номер документа, кем выдан, даты выдачи/истечения | БИН, юридический адрес (офис), руководитель компании, ИИК (номер счёта), банк, БИК |

На карточке клиента для юр. лица вместо блока «Документ» показывается блок «Реквизиты».
Переменные шаблонов `{{client_bin}}`, `{{client_address}}`, `{{client_director}}`,
`{{client_account}}`, `{{client_bank}}`, `{{client_bik}}` берут реальные значения
(раньше были заглушками: БИН подставлялся из ИИН, руководитель — из названия, остальные пустые).
Реквизиты добавлены в импорт/экспорт клиентов.

### Мастерская (`/workshop`)
Канбан: **Новая → В работе → Готово → Архив**, перетаскивание карточек.
Заявки создаются вручную или автоматически при возврате товара с профилактикой/ремонтом.
Запчасти и услуги с автоподсчётом. Аналитика поломок.
При переводе в «Готово» товар возвращается в `available`.

### Документы (`/documents`)
**WYSIWYG-редактор на TipTap:**
- Визуальный лист А4, тулбар (жирный/курсив/подчёркнутый, выравнивание, списки, таблицы)
- **Импорт Word** (.docx) через mammoth
- Правая панель с **80+ переменными**: Компания / Общее / Аренда / Клиент / Продукты
- Вставка переменной в позицию курсора по кнопке `+`

**В карточке аренды** — блок «Документы»: выбор шаблона → генерация с подстановкой
данных → просмотр, печать, удаление.

**Стили готового документа — `src/lib/document-styles.ts`, один набор на предпросмотр
и на печать.** Раньше окно печати открывалось вообще без CSS: рамки таблиц рисовало
правило `.ProseMirror table` из `globals.css`, которое в новом окне не действует.
Из-за этого таблицы теряли границы и заливку, а браузерный Times 16px раздувал документ
на лишнюю страницу.

- `DOCUMENT_CSS` повторяет правила редактора (таблицы, заголовки, списки, размер шрифта)
- `DOCUMENT_PRINT_CSS` добавляет `@page { size: A4; margin: 14mm 12mm }`,
  запрет разрыва строк таблицы и **`print-color-adjust: exact`** — без него браузер
  выбрасывает заливку ячеек и цветной текст при печати
- предпросмотр показывает документ листом А4 с теми же полями, что и печать
- лист в редакторе тоже получил поля `14mm`, чтобы переносы строк в шаблоне и в готовом
  документе совпадали

Меняете вид таблиц — правьте `DOCUMENT_CSS` и `.ProseMirror` в `globals.css` вместе,
иначе редактор и печать разъедутся.

Суммы «текстом» (`{{total_text}}` → «шесть тысяч тенге») для договоров.

### Воронка (`/funnel`) — заявки

Доска входящих заявок: клиент позвонил, менеджер завёл карточку и указал, **когда клиенту
нужен инструмент**. Пункт меню стоит под «Клиентами».

**Колонки:** Клиенты на сегодня · Нужно на завтра · Нужно на этой неделе ·
Нужно в будущем · Нет в наличии.

**Главное решение: колонка НЕ хранится в базе.** Она вычисляется из `needed_at` функцией
`leadBucket()` в `src/lib/funnel.ts`. Поэтому заявка «на завтра» сама оказывается
в «сегодня», когда наступает завтра, — и это работает без фонового задания, которое
может не отработать или сдвинуть все карточки, если сервер простоял ночь выключенным.
Проверено на границе полуночи: 6 сентября 23:59 — «завтра», 7 сентября 00:01 — «сегодня».

- **Просроченные не теряются:** вчерашние и более старые тоже попадают в «сегодня»,
  дата на карточке краснеет
- «Нет в наличии» — ручной флаг `unavailable`, он сильнее даты
- Страница пересчитывает колонки **раз в минуту** (`setInterval`), чтобы вкладка,
  открытая со вчера, не показывала вчерашнюю картину
- Перетаскивание карточки в другую колонку **меняет дату** (`dateForBucket()`),
  а не какой-то отдельный статус. На телефоне вместо перетаскивания — выпадающий список

**Закрытие сделки:** пока карточку тащат, внизу появляются две полосы —
«Успешно завершено» и «Не реализовано». Статус `status`: `open` / `won` / `lost`.
Закрытые уходят с доски на отдельные вкладки — иначе через полгода в браузер
уезжали бы тысячи мёртвых карточек.

**Права:** `leads.view` — просмотр, `leads.edit` — создание и изменение.

**Фильтры:** поиск (инструмент, клиент, телефон, номер — с задержкой 300 мс, чтобы
не дёргать сервер на каждую букву), менеджер, канал привлечения. Фильтрация и итоги
в шапке считаются в SQL.

Нумерация заявок сквозная (`№1, №2…`), как в референсе.

**Заявка → аренда одной кнопкой.** В карточке заявки кнопка «Оформить аренду»
(нужно право `rentals.edit`):

1. `POST /api/leads/[id]/convert` ищет клиента **по телефону без учёта форматирования**
   (`+7 707 370-51-31` и `87073705131` — один человек, сравниваются последние 10 цифр).
   Нашёлся — берём его, нет — заводим нового с каналом привлечения из заявки.
   Повторное нажатие дубля не создаёт.
2. Открывается обычная форма аренды `/rentals/new?client=…&lead=…&title=…&needed=…`
   с подставленным клиентом и датой начала из заявки, сверху — плашка с тем,
   что клиенту нужно.
3. После «Забронировать аренду» заявка автоматически закрывается как успешная.

Саму аренду эндпоинт не создаёт намеренно: инструмент, сроки, залог и оплату собирает
менеджер в существующей форме, дублировать эту логику ради одной кнопки незачем.

Параметры в форме аренды читаются из `window.location.search`, а не через
`useSearchParams` — тот требует обёртки в `Suspense` и ломает пререндер страницы.

### Темп (`/tasks`) — задачи сотрудников и KPI

Доска в духе Trello: колонки **Новая → В работе → На проверке → Выполнена → Отменена**,
перетаскивание карточек мышью, на телефоне статус меняется выпадающим списком.
Пункт меню стоит над «Настройками».

**Права:**

| Право | Что даёт |
|---|---|
| `tasks.view` | Свои задачи: где сотрудник исполнитель или постановщик, плюс те, что ему открыли |
| `tasks.manage` | Все задачи, постановка, назначение исполнителя, сроки, вес, удаление и KPI по всем |

**Видимость задачи** — исполнитель, постановщик и те, кого явно отметили в блоке
«Кому ещё видна задача». Список зрителей лежит в отдельной таблице `task_viewers`
(а не JSON-полем), чтобы выборка шла по индексу.

**Ограничения на изменение** (`PATCH /api/tasks/[id]`): с `tasks.manage` меняется всё;
исполнителю разрешён только собственный статус — сроки, вес и список зрителей он не
подкрутит. Проверка серверная, не в интерфейсе.

**KPI** — вкладка рядом с доской, периоды 7 / 30 / 90 дней и всё время:

- баллы: вес выполненных задач (задаётся при постановке, рутина 1, крупная 3–5)
- в срок и с опозданием, среднее время выполнения
- сводная оценка 0–100: **60% — доля закрытых задач, 40% — доля закрытых в срок**;
  задачи без срока считаются выполненными вовремя

Момент выполнения фиксируется в `done_at` при переводе в «Выполнена» и **сбрасывается**
при возврате в работу — иначе KPI можно было бы накрутить перекладыванием карточки.

**Что сделано ради нагрузки** (раздел добавлялся с оглядкой на то, что функций уже много):

- задачи **не входят** в общий `store.hydrate()` — он тянется на каждой странице,
  а «Темп» нужен не всем. Страница грузит свои данные сама
- фильтр видимости стоит в SQL, а не на клиенте: чужие задачи не уезжают в браузер даже в ответе
- KPI считается одним агрегатом в SQLite, а не переносом всех задач в JS
- индексы `idx_tasks_assignee`, `idx_tasks_status`, `idx_tasks_done_at`, `idx_task_viewers_user`;
  выборка «мои задачи» идёт по индексу (проверено `EXPLAIN QUERY PLAN`)
- список задач ограничен 300 записями на запрос
- список сотрудников отдаёт общий лёгкий `/api/staff` (id, имя, должность), а не
  `/api/users` с правами и хешами. Им пользуются и «Темп», и «Воронка»
- перенос карточки применяется оптимистично и откатывается, если сервер отказал

## 3.1 Мобильная версия

Приложение адаптировано под телефон 9:16 (проверялось на 375×812).

**Ключевое правило: на компьютере интерфейс остаётся прежним при любой ширине окна.**
Мобильная раскладка включается по УСТРОЙСТВУ, а не по ширине — сузили окно браузера
на десктопе, интерфейс не меняется.

**Как определяется телефон** — `src/lib/use-is-mobile.ts`, хук `useIsMobile()`:
- user-agent телефона/планшета, **или**
- iPadOS 13+ (представляется Mac'ом — ловим по `maxTouchPoints > 1`), **или**
- `pointer: coarse` И при этом `any-pointer: fine` отсутствует, то есть мыши в системе нет
  (ноутбук с сенсорным экраном сюда НЕ попадает — у него есть точный указатель)

До монтирования возвращает `false` — иначе разъезжается гидратация.

На хук завязаны все перестроения раскладки: выдвижное меню, стопка колонок в карточке
аренды, в форме новой аренды, в редакторе документов и в шапке каталога.
Медиа-запрос мобильных стилей в `globals.css` тоже сужен до `(pointer: coarse)`.

**Оболочка** (`app-shell.tsx`):
- на телефоне боковая панель превращается в выдвижное меню (`Sidebar mobile open onClose`)
  с затемнением; закрывается по тапу на фон, по крестику и при переходе по ссылке
- вместо неё сверху — `MobileTopBar`: бургер, логотип, кнопка «+» на новую аренду
- под открытым меню body не прокручивается
- высота везде `100dvh`, а не `100vh` — иначе адресная строка мобильного браузера обрезает низ

**Что сделано по разметке:**
- `export const viewport` в `layout.tsx` — без него мобильный браузер рендерит страницу
  в ширине 980px и ужимает её; там же `viewportFit: "cover"` и `themeColor`
- утилиты `.safe-top` / `.safe-bottom` под чёлку и домашнюю полосу iOS
- **поля ввода на телефоне 16px** — при меньшем размере iOS зумит страницу на фокусе
- двухколоночные формы (клиент, инвентарь, комплект, настройки, пользователи) —
  в один столбец до `sm`
- двухколоночные экраны (карточка аренды, форма новой аренды, редактор документов) —
  стопкой **на телефоне** (через `useIsMobile()`, не через брейкпоинт), боковые панели
  во всю ширину вместо `w-[340px]`
- модалки на телефоне приезжают снизу на всю ширину со скруглением только сверху,
  высота `92dvh`, прокрутка внутри
- вкладки каталога и переключатели периодов не переносятся, а прокручиваются по горизонтали;
  кнопки действий уходят на строку ниже **только на телефоне**
- фильтры каталога на телефоне — сетка 2×N вместо ряда
- таблицы прокручиваются горизонтально внутри карточки (`TableCard`)
- hover-эффекты отключены при `(hover: none)` — на тапе они залипали

## 3.2 Периоды в аналитике и финансах

Общий переключатель — `src/components/ui/period-picker.tsx`, общая логика — `src/lib/period.ts`.
Обе страницы используют одно и то же, чтобы не разъезжались.

- Быстрые кнопки: `day` (24 часа), `week`, `month`, `year`, `all`
- Кнопка «Выбрать даты» открывает два поля и кнопку «Применить»; выбранный диапазон
  показывается прямо на кнопке (`01.09.2026 — 06.09.2026`)

**Границы диапазона считает браузер, а не сервер.** Пользователь выбирает даты в своём
часовом поясе, а `created_at` в базе лежит в UTC: клиент превращает `2026-09-01` в
`2026-09-01T00:00:00` по местному времени и отправляет готовый ISO. Сервер их только проверяет.

**Шаг графика (`granularity`) выбирает сервер** и возвращает вместе с данными:

| Период | Шаг |
|---|---|
| 24 часа, свой диапазон до 2 суток | по часам |
| 7 и 30 дней, свой диапазон до 92 дней | по дням |
| 12 месяцев, всё время, свой диапазон длиннее 92 дней | по месяцам |

Без этого сутки рисовались бы одним столбцом, а год — тремя сотнями.

**Важно при доработке запросов:** у всех выборок с периодом теперь ДВЕ границы —
`created_at >= ? AND created_at <= ?`. Раньше была только нижняя, и произвольный
диапазон молча захватывал всё до сегодняшнего дня. Добавляете новую метрику за период —
не забудьте верхнюю границу.

## 6. Грабли (не наступать снова)

1. **`secure: true` на cookie ломает сессию на Railway.** Reverse proxy: браузер видит
   HTTPS, внутри HTTP → куки не передавались, выкидывало на логин. В `src/lib/session.ts`
   стоит `secure: false`.

2. **`tsconfig.tsbuildinfo` ломает Docker-сборку** (`not a directory`). Убрали
   `"incremental": true` из `tsconfig.json`, файл в `.gitignore`.

3. **`healthcheckPath` должен быть `/login`.** На `/` и `/api/auth/me` — Healthcheck failure.

4. **В таблице `rentals` НЕТ колонки `client_json`.** Клиент через `client_id`.
   Из-за `r.client_json` крашились `/api/analytics` и `/api/finance`.
   Используйте `JOIN clients c ON c.id = r.client_id`.

5. **`serverExternalPackages: ["better-sqlite3", "bcryptjs"]`** в `next.config.ts` обязателен.

6. **`src/instrumentation.ts` ломает сборку** если импортирует better-sqlite3.
   Планировщик запускается при импорте `repo.ts` с защитой `global.__penaltySchedulerStarted`.

7. **Next.js 15:** `params` — это `Promise`, нужен `await params`
   (или `use(params)` в клиентских компонентах).

8. **Новые колонки в существующих таблицах — только через `ensureColumns()` в `db.ts`.**
   `CREATE TABLE IF NOT EXISTS` не меняет структуру уже созданной таблицы, поэтому на боевой
   базе новое поле появится только через `ALTER TABLE ADD COLUMN`. Хелпер сверяется с
   `PRAGMA table_info` и **глотает ошибку `duplicate column name`**: воркеры сборки Next
   импортируют модуль параллельно и без этого первый деплой падает.

9. **Вся схема создаётся одним `db.exec`.** При сборке Next поднимает несколько воркеров,
   каждый импортирует `db.ts`; если разбить DDL на два вызова, первый прогон на пустой базе
   падает с `SQLITE_BUSY: database is locked`. Новые таблицы добавлять внутрь существующего
   блока, а не отдельным `db.exec`.

10. **Даты аренды хранятся только в `start_at`/`end_at`.** Поля `startDate`/`endDate`
    в домене — производные (`.slice(0, 10)` от ISO), их заполняет `rentalRowToDomain`.
    Раньше они возвращались пустыми строками: в карточке и в списке аренд даты не
    отображались, а «Выручка за сегодня» на главной (фильтр `startDate.startsWith(today)`)
    всегда показывала 0. Для показа пользователю берите `formatDateTimeDisplay(startAt)`,
    для сравнения по дню — `startDate`.

11. **Мобильную раскладку включать по устройству, а не по `max-width`.** Первая версия
    адаптива ориентировалась на ширину окна — и на компьютере с узким окном пользователь
    получал мобильный интерфейс, чего быть не должно. Новые мобильные правила вешать
    на `useIsMobile()` или на `(pointer: coarse)`, а не на голый брейкпоинт.

12. **`useIsMobile()` до монтирования обязан возвращать `false`.** Сервер не знает ширину
    окна: если хук сразу вернёт `true`, серверная и клиентская разметка разойдутся и React
    выбросит hydration error.

13. **Не запускать `npm run build` при работающем `npm run dev`.** Продакшен-сборка
    перезаписывает `.next`, дев-сервер начинает отдавать `Internal Server Error`
    (`Cannot find module './xxxx.js'`). Лечится: остановить dev, `rm -rf .next`, запустить заново.

14. **Hydration error от расширений браузера** (`bis_register`) — решено через
   `suppressHydrationWarning` на `<html>`/`<body>` + флаг `mounted` в `AppShell`.

## 7. Принципиальные решения

- **Никаких фейковых данных.** Дашборд стартует с нуля. `mock-data.ts` — только справочники.
- **Источник истины — SQLite на сервере.** Zustand — только кэш. Если что-то не отображается,
  проверить что `StoreHydrator` смонтирован.
- **Всё только из каталога.** Товары, комплекты и услуги выбираются из справочников,
  ручной ввод в форме аренды убран.
- **Продукт — это группа единиц по названию, а не отдельная сущность.** Поштучный учёт
  (аренда, мастерская, QR, возврат по состоянию) завязан на единицу и остаётся нетронутым.
- **Права проверяются и в UI, и в API.** Не использовать `if (user.role === "admin")`.
