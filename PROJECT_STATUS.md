# QURAL-SAIMAN — статус проекта

CRM для аренды строительного инструмента. Казахстан, Атырау. Валюта — тенге (₸).
Развёрнут на Railway, автодеплой из GitHub.

**Как использовать:** прочитайте этот файл первым в новой сессии — здесь всё текущее
состояние, архитектурные решения и грабли, на которые уже наступали.

## 1. Стек

- **Next.js 15.5** (App Router) + React 19 + TypeScript + Tailwind CSS 4
- **SQLite** через `better-sqlite3` — `data/app.db` локально, `/data/app.db` на Railway
- **REST API** — Next.js route handlers (`src/app/api/**`)
- **Zustand** (`src/lib/store.ts`) — клиентский кэш поверх API, НЕ источник истины
- **iron-session** + **bcryptjs** — авторизация и хеширование паролей
- **TipTap** — WYSIWYG-редактор шаблонов документов
- **Recharts** — графики в Аналитике и Финансах
- **mammoth** — импорт Word (.docx) в редактор шаблонов
- **qrcode** — QR-коды инвентаря, **xlsx** — импорт/экспорт клиентов

**Дизайн — «тёплый минимал»** (тема переделана, тёмная панель и фиолетовый акцент убраны):

| Меню | `#F2F0EA` тёплый песок | `--color-sidebar` |

Скругления 12–16px, мягкие тени. Тень акцентных кнопок вынесена в `--shadow-primary`.

**Шрифт — Onest** (один на весь интерфейс, у него хорошая кириллица), заголовкам задан
трекинг `-0.015em`. Manrope и Inter больше не подключаются.

**Тёмная тема.** Переключатель в «Настройки → Оформление»: Светлая / Тёмная / Как в системе.
Выбор хранится в `localStorage` под ключом `qs-theme` — это настройка браузера, а не аккаунта,
у разных пользователей она своя.

- `src/components/layout/theme-provider.tsx` — контекст `useTheme()`, ставит на `<html>`
  атрибут `data-theme="light|dark"` и следит за системной темой в режиме «как в системе»
- В `layout.tsx` есть **блокирующий скрипт** `themeBootstrap`, который выставляет атрибут
  до первой отрисовки. Без него страница мигает светлым, пока не смонтируется провайдер
- Тёмная палитра: фон `#0A0A0B`, поверхности `#141417`, меню `#101012`,
  акцент `#17B892` (мята), текст на акценте `#04211B`

**`--color-on-primary`** — текст и иконки поверх акцентной заливки. В светлой теме белый,
в тёмной почти чёрный: на мятной кнопке белый текст нечитаем. Все кнопки с
`bg-[var(--color-primary)]` используют этот токен, а не `text-white`.

**Слой перекраски статусов** в конце `globals.css`. Статусные цвета (пастель + насыщенный
текст) зашиты в классы Tailwind примерно в 250 местах по проекту. Вместо их переписывания
в тёмной теме переопределяются конкретные утилиты:

```css
:root[data-theme="dark"] .bg-[#EAF7EE] { background-color: var(--tone-green-bg); }
```

Обратные слэши обязательны — Tailwind экранирует `[`, `#` и `]` в имени класса.
Без них правило невалидно и браузер молча его выбрасывает. Добавляете новый пастельный
цвет — добавьте и правило сюда, иначе в тёмной теме он останется светлым пятном.

**Правила по цвету:**
- Новые элементы красить только через переменные, хардкод hex акцента не заводить
- Статус аренды «Забронировано» переведён с фиолетового на синий `#2B5FD9` — изумруд
  занят акцентом, а зелёный «Завершено»
- Меню светлое: белого текста в `sidebar.tsx` и `mobile-topbar.tsx` не должно быть,
  кроме как на акцентной заливке — там `text-[var(--color-on-primary)]`
- Поверхности красить `bg-[var(--color-surface)]`, а не `bg-white` — иначе карточка
  останется белой в тёмной теме

## 2. Авторизация и права (RBAC)

### Вход
- Страница `/login`, тёмная, логотип QURAL-SAIMAN
- Главный администратор создаётся автоматически: **логин `admin`, пароль `admin`**
- Сессия — cookie `rental_crm_session` через iron-session, 7 дней

### Две роли поверх прав

| Роль | Что даёт | Кто выдаёт |
|---|---|---|
| **Главный администратор** (`is_owner`) | Полный доступ и единственное право раздавать роль администратора. Его нельзя удалить, заблокировать или разжаловать | Заводится сам при первом запуске — логин `admin` |
| **Администратор** (`is_admin`) | Полный доступ ко всем разделам без отдельных галочек — роль для руководителя | Только главный администратор |
| Сотрудник | Ровно то, что отмечено галочками | Любой с правом `users.edit` |

- Роль выдаётся галочкой «Права администратора» в карточке пользователя — она
  видна только главному администратору
- Галочки прав при выдаче роли **не стираются**: заберут роль — человек вернётся
  к своим прежним разделам
- Роль применяется **сразу, без перезахода**: `getCurrentUser()` перечитывает
  пользователя из базы, а не верит cookie. Заблокировали — доступ обрывается тем
  же запросом (401)

### Права (25 разрешений)
```
dashboard.view
rentals.view / rentals.edit
catalog.view / catalog.edit
clients.view / clients.edit
workshop.view / workshop.edit
documents.view / documents.edit
blacklist.view
leads.view / leads.edit
delivery.view / delivery.edit
shop.view / shop.edit
tasks.view / tasks.manage
analytics.view
finance.view
settings.view
users.view / users.edit
```

- `isAdmin: true` → полный доступ, права не проверяются
- Пункты меню в сайдбаре скрываются если нет права
- Проверка на уровне API через `requireAuth("permission")` в `src/lib/auth.ts`

### Страница `/users`
Создание, редактирование, блокировка, удаление. Права чекбоксами по группам +
кнопки «Выбрать все» / «Снять все».

**Безопасность:**
- Главного администратора нельзя удалить, заблокировать или лишить полного доступа
- Его пароль меняет только он сам (кнопка 🔑 видна лишь в своей строке)
- Назначенного администратора редактировать, блокировать и удалять можно — это
  обычный пользователь, которому выдали полный доступ
- Себя нельзя ни удалить, ни заблокировать: иначе легко запереть себя снаружи
- Все запреты живут в `repo.ts` и роутах, а не в интерфейсе

## 3. Что полностью работает

### Аренды (`/rentals`)

**Нумерация сквозная, по порядку создания** (№1, №2, №3…). Номер присваивает **сервер**
в `createRental`, значение из тела запроса игнорируется — на клиенте два менеджера
могли бы одновременно получить одинаковый номер.

Счётчик лежит строкой `rental_counter` в `company_settings` и только растёт:
`MAX(number)` не годится (у аренд, созданных до этого, номер — обрывок метки времени
вроде `806978`), а `COUNT(*)` дал бы дубли после удаления аренды. При первом обращении
счётчик стартует с числа уже существующих аренд.

В базе номер лежит **без решётки**, «№» подставляет интерфейс. У старых записей решётка
срезается при чтении (`rentalRowToDomain`), поэтому вид одинаковый. В шаблонах документов
`{{rental_number}}` тоже без решётки — она уже есть в тексте шаблона (`АКТ №{{rental_number}}`).

Цикл: **запрос → забронировано → в аренде → завершено / просрочено / украдено / отменено**

**Вкладки:** Все / Запрос / Забронировано / В аренде / Завершено / Просрочено /
Должники / Украдено / Отменено / Архив

**Должники** — только `active`/`overdue` + `total > paid` (неоплаченные брони не попадают)

#### Форма новой аренды (`/rentals/new`)
- Поиск клиента или создание нового (модалка с полями документов)
- **Предупреждение о ЧС** — при выборе клиента из чёрного списка открывается блокирующая
  модалка со списком краж (номер, товары, сумма) и просрочек. Кнопки:
  «Да, оформить (беру ответственность)» / «Отмена»
- Пункт проката: **Атырау по умолчанию**, ещё есть Астана
- Товары **только из каталога**, ручной ввод убран
- **Мультивыбор товаров** — чекбоксы, при выборе можно поменять цену за сутки
- **Комплекты и услуги тоже выбираются из каталога** (`add-catalog-bundle-modal.tsx`),
  ручной ввод убран полностью
- Компактные карточки по категориям (Продукты / Комплекты / Услуги)
- Модалка оплаты: тип (Оплата компаний / Наличные / Kaspi QR) + сумма
- Кнопки «Сохранить изменения» (`request`) и «Забронировать аренду →» (`booked`)

#### Карточка аренды (`/rentals/[id]`)
Правая панель `rental-side-panel.tsx` — все действия:

| Действие | Условие | Что делает |
|---|---|---|
| **Выдать в аренду** | `booked` | → `active`, `issuedBy` из сессии. Если не оплачено — предупреждение «попадёт в Должники» |
| **Принять оплату** | остаток > 0 | Модалка: тип оплаты + сумма → `paid`, `paymentStatus` |
| **Скидка** | всегда | Модалка: ₸ или %, предпросмотр итога → уменьшает `total` |
| **Возврат средств** | `paid > 0` | Модалка: сумма → уменьшает `paid` |
| **Возврат товара** | оплачено + `active`/`overdue` | **Мультивыбор** с чекбоксами, у каждого товара состояние: Исправен / Профилактика / Ремонт. Частичный возврат оставляет аренду активной |
| **Украдено** | `active`/`overdue` | Модалка → товары `stolen`, аренда `stolen`, клиент в ЧС |
| **Товар возвращён клиентом** | `stolen` | Модалка: убрать из ЧС или оставить. Товары → `repair`, аренда → `completed` |
| **Залог** | всегда | Модалка: тип (Денежный/Оборудование/Документ) + сумма |
| **Авто-штраф** | всегда | Модалка: переключатель + ставка ₸/час |
| **Ручной штраф** | всегда | Модалка: причина + сумма → прибавляется к `total` |
| **Расходы** | всегда | Модалка: тип + сумма |
| **Заметки** | всегда | Сохраняются в БД, отправка по Enter |

#### История аренды, паузы и откат ошибок

В шапке карточки — кнопка паузы и меню «…»: История аренды · История пауз ·
Отменить аренду · Удалить аренду.

**История аренды** (`rental_events`). Записи делает не интерфейс, а `updateRental`:
он сравнивает аренду до и после изменения и пишет только то, что реально поменялось —
статус, оплата, сумма, состав, даты. Один разбор в репозитории вместо десятка ручных
вызовов по кнопкам, иначе часть действий неизбежно забыли бы залогировать.

**Откат ошибочного действия.** У события хранится `before_json` — значения полей ДО
изменения. Кнопка отмены применяет их обратно (`revertRentalEvent`), помечает событие
`reverted = 1` и **записывает сам факт отката отдельной строкой** — из журнала ничего
не исчезает. Повторно откатить то же событие нельзя (400). Откат идёт через
`updateRental(..., { silent: true })`, иначе он сам породил бы новое событие и история
зациклилась бы.

**Паузы** (`rental_pauses` + колонка `rentals.paused_at`). Пауза — не статус, а флаг:
аренда остаётся «В аренде», рядом появляется бейдж «На паузе».

- на паузе аренда **не просрочивается и не копит штрафы** — планировщик
  `applyOverdueAndPenalties` отбирает записи с `paused_at IS NULL`
- при снятии с паузы **дата возврата сдвигается на время простоя**: иначе клиент,
  у которого работы встали не по его вине, получил бы просрочку
- «История пауз» показывает каждый простой с длительностью и суммарное время

**Удаление аренды** освобождает занятый инвентарь и удаляет её документы, события и паузы.
Колонка `paused_at` добавляется в существующую таблицу через `ensureColumns`.

**Редактирование дат** — кнопка «✏ Изменить даты», два поля `datetime-local`,
продолжительность пересчитывается на лету. Комментарий тоже редактируется.

**Менеджер** — из активной сессии (`useAuth()`), не захардкожен.

#### Некомплект при возврате
Пылесос вернули, а трубку «потеряли». В модалке возврата у каждой позиции есть галочка
**«Комплект полный»** — снимаете её и пишете, чего не хватает.

- Инструмент всё равно принимается: вещь уже у нас, держать аренду открытой незачем
- Запись попадает на отдельную страницу **«Некомплект»** (`/shortages`). В шапку «Аренд»
  вынесена только кнопка с красным счётчиком открытых вопросов
- Страница — список с вкладками «Открытые / Закрытые / Все». В строке: что и чего не хватает,
  кто принял, клиент целиком (имя-ссылка на карточку, тип, телефон, почта, рейтинг, число аренд
  и просрочек), ссылка на аренду
- Кнопки в строке: «Вопрос закрыт» — когда деталь вернули или оплатили (закрытые можно открыть
  заново) и **«Заблокировать клиента»** — тот же чёрный список, что и при краже. Кнопка блокировки
  требует права `clients.edit`, закрытие вопроса — `rentals.edit`
- Данные клиента берутся из стора (там рейтинг и история), а если карточка ещё не подгрузилась —
  из самой записи: имя, телефон, почта и тип копируются в ответ `/api/shortages`
- Всё пишется и в историю аренды: «Принял с некомплектом», «Некомплект закрыт»

#### Чек оплаты
Каждый платёж показывается отдельной строкой в блоке «К оплате» — сразу под кнопками,
над «Документами»: чем платили, сколько, когда и **кто принял деньги** (`created_by`
в `rental_payments`). Одна итоговая цифра «оплачено» на вопросы не отвечает:
спорят обычно не про сумму, а про то, пришли деньги по Kaspi или наличными
и кто их взял.

#### Возврат товара
Кнопка «Возврат товара» доступна при статусах «В аренде» и «Просрочено» **независимо от
оплаты**: инструмент нужно забрать в любом случае, а деньги — отдельный разговор.

- Если долг остался, в модалке видно предупреждение с суммой, а при завершении аренде
  ставится `paymentStatus: overdue`
- Завершённая аренда с остатком **остаётся во вкладке «Должники»** (`isDebtorRental()` в
  `utils.ts`). Раньше фильтр смотрел только на `active`/`overdue`, и после возврата товара
  долг пропадал из виду
- В списке возврата только арендный инвентарь: товары магазина проданы и не возвращаются
- Момент возврата пишется в `rentals.returned_at` и идёт в рейтинг клиента

#### Правки прямо в карточке
Даты и комментарий редактируются на месте — без кнопки «Изменить». Кнопка
**«Сохранить изменения» живёт в верхней планке** и появляется, только когда есть
что сохранять.

- **Продление сразу считает деньги**: под полями видно «Продление на 3 сут. —
  доплата 15 000 ₸», новую сумму аренды и остаток к оплате
- Считаем **дельту** по ставке за сутки, а не сумму заново: пересчёт с нуля затёр
  бы ручные скидки и штрафы
- **Позиции добавляются в открытую аренду** — товар, комплект, услуга, магазин.
  Клиент часто возвращается за вторым инструментом через пару часов. Счёт
  поднимается сам, лишнюю позицию можно убрать — сумма уменьшится
- Срок считается функцией `durationDays()`, она отбрасывает секунды: аренда
  «с 12:15 до 12:15 следующего дня» раньше превращалась в двое суток из-за одной
  лишней миллисекунды в дате

### Автоматический пересчёт при просрочке
`applyOverdueAndPenalties()` в конце `src/lib/repo.ts`:
- Аренды `active`/`booked`/`overdue` с `end_at` в прошлом → статус `overdue`
- **Пересчёт `total` по фактическим дням**: взял на 3 дня по 1000₸ (`total=3000`),
  вернул через 5 дней → `total=5000`. Услуги не умножаются на дни.
- Если включён почасовой штраф — пересчёт по дням НЕ применяется (чтобы не дублировать)
- `total` только растёт
- Запуск: раз в час фоном + при GET `/api/rentals/[id]` + вручную `GET /api/cron`

### Каталог (`/catalog`)
Пять вкладок в одной странице: **Продукты · Комплекты · Услуги · Инвентаризация · График занятости**.
Кнопка действия справа от вкладок меняется под активную вкладку, доступна только с правом `catalog.edit`.

#### Продукты
Запись в БД по-прежнему = одна физическая единица (свой артикул, QR, статус, блокировка при аренде).
Вкладка **группирует единицы по названию** и показывает их свёрнутыми — отдельной вкладки
«Инвентари» нет намеренно, единицы раскрываются стрелкой в строке продукта.

- Таблица: Название · Категория · Артикул · Доступность (`2/2 Свободно`) · Неисправно · Цена.
  Артикул группы — общий, если у всех единиц один, иначе диапазон `QS.0001…QS.0003`
- Статистика: Продукт / Кол-во / Свободно / Забронировано / В аренде / Неисправно / На ремонте /
  Списано-украдено. «Забронировано» считается из аренд в статусе `booked`/`request`
- Фильтры: поиск, пункт проката, категория, тип продуктов, «Только свободные», экспорт в Excel
- Кнопка **«Неактивные инвентари»** переключает список на украденные и списанные единицы
- В форме добавления есть поле **«Количество единиц»** — создаёт N записей, каждой свой артикул
- **Артикул присваивается автоматически, если поле оставили пустым** (`nextSku()` продолжает
  существующую нумерацию: `QS.0001, QS.0002…`). Без артикула не построить QR-код, поэтому
  пустым он больше не остаётся

Статусы единицы: `available`, `rented`, `maintenance`, `repair`, `stolen`, `written_off`.

**QR-код** содержит JSON `{id, sku, name, category, url}`. Кнопка «Распечатать QR»
открывает окно с QR + данными товара и вызывает печать.

#### Комплекты (таблица `kits`)
Название, категория, фото, цена за сутки, состав из позиций. Позиция может быть **привязана
к продукту каталога** — тогда доступность комплекта считается как минимум по составу
(`kitAvailability`); если привязок нет, показывается «∞ Свободно».
Статистика: кол-во комплектов, свободно, общая выручка (из аренд по названию).

#### Услуги (таблица `services`)
Название и **тарифы**: День / разовая / за период, у каждого своя цена
(показываются как «День (разовая,за период)» — как в референсе).
Статистика: кол-во услуг, общая выручка, средний чек.

#### Инвентаризация (таблица `inventory_checks`)
Две подвкладки: **Список для проверки** и **История проверок**.
Фильтры по состоянию: Все / Исправен / Сломан / Не проверено (со счётчиками).
Колонки: Инвентарь · Артикул · Статус · Состояние · Проверял · Последняя аренда · Последняя проверка.
Кнопка «Проверить» пишет запись (кто, когда, состояние, комментарий). Если отмечено
**«Сломан» и единица свободна** — она переводится в статус `repair` и перестаёт попадать
в новые аренды (единицы в аренде и украденные не трогаются).

#### График занятости
Диаграмма Ганта: строки — единицы инвентаря, колонки — дни выбранного периода
(по умолчанию текущий месяц, максимум 190 дней). Полосы аренд кликабельны и ведут на карточку,
цвет — по статусу аренды, сегодняшний день подсвечен. Фильтры: поиск, период, категория,
пункт проката. Легенда Исправен / Сломан.

#### Импорт из старой системы
Кнопка «Импорт» в каталоге (вкладка «Продукты») и в меню «Добавить» на странице
клиентов. **Видна только главному администратору**, роуты отвечают 403 всем
остальным: загрузка чужой выгрузки необратима.

Файл читается в браузере (`inventory-io.ts`, `client-io.ts`), на сервер уходит уже
разобранный список. Формат прошлой системы понимается как есть:

| Каталог | Клиенты |
|---|---|
| `ID, Название, Артикул, Категория, Доступность, Количество, Дата создания, тарифы…` | `ID, ФИО/Название компании, Вид, Контакты, Дата добавления, Рейтинг, Бонусы, Канал…` |

Что при этом происходит:

- **Тарифные колонки распознаются по заголовку** — «День (1 д.)», «3 дня (3 д.)»,
  «Час (1 ч.)». В карточку кладём цену за сутки: дневной тариф как есть, иначе
  пересчитываем ближайший
- **Строка каталога разворачивается в единицы**: «Количество: 3» заводит три записи,
  учёт в системе поштучный. Артикул из файла достаётся первой, остальным система
  присваивает свои
- **«Доступность» не импортируется** — она считается по активным арендам
- **`QS` без номера — не артикул**, а остаток шаблона: такие получают свой номер
- **Колонка «Рейтинг» у клиентов — не звёзды, а метки**: «Черный список» переводится
  во флаг, «Умер» и прочее сохраняется в заметку. Звёзды у нас считаются сами
- **Дубли схлопываются по телефону**, а у кого его нет (в выгрузке там один плюс) —
  по имени. При схлопывании строка-дубль **дополняет карточку**: чёрный список,
  тип «юр. лицо», пометка и пустые поля переносятся, заполненное не затирается
- **Клиенты без телефона всё равно заводятся** — это живая история, терять её нельзя
- **Накопленные суммы («Кол-во заказов», «Сумма аренд») не читаются**: они считаются
  по реальным арендам, подставлять из файла — врать в отчётах
- Всё одной транзакцией; после загрузки показывается отчёт: сколько добавлено,
  сколько пропущено и по каким причинам

**Порядок важен: каталог → клиенты → аренды.** Аренда цепляется к уже загруженным
карточкам: клиент ищется по телефону (затем по имени), позиции — по артикулу.

**Аренды** (`№ | ФИО | Телефон | Статус | Начало | Факт. начало | Конец | Факт. конец |
`Стоимость без скидки | Стоимость аренды | Оплаченная сумма | Дата добавления | Инвентари`):

- Статусы переводятся: «В аренде» → `active`, «Просрочено» → `overdue`, «Завершено» →
  `completed`, «Отменено» → `cancelled`. **«Должник» — не статус, а долг**: такая аренда
  закрывается как `completed` с `paymentStatus: overdue` и попадает во вкладку «Должники»
- **«Факт. конец аренды» ложится в `returned_at`** — по нему считается пунктуальность
  клиента в рейтинге. «Факт. начало» не читаем: начало у нас одно, договорное
- Состав аренды приходит строкой `Название (АРТИКУЛ), Название (АРТИКУЛ)` — режем по
  скобкам, а не по запятым: в названиях инструментов запятые встречаются
- Позиции привязываются к каталогу по артикулу, а **чего нет — заводится само**:
  выгрузка каталога сгруппирована по продуктам, артикулов конкретных единиц
  (`QS.0404` и таких же) в ней нет, а в арендах они есть. Раз единицу выдавали —
  она существовала, значит ей место в каталоге. Название берётся из аренды, цена и
  категория — у одноимённых позиций каталога
- Новая единица заводится один раз на артикул и всегда со статусом «свободна»:
  занятость проставляется отдельно и только по идущим арендам
- Клиента, которого нет в базе, заводим на лету — иначе аренду некуда положить
  (внешний ключ). Сколько таких, видно в отчёте
- **Инструмент помечается занятым только у идущих аренд** (`active`/`overdue`):
  три тысячи закрытых аренд не должны запирать каталог
- Скидка (разница «без скидки» и «аренды») сохраняется комментарием к аренде
- Дедупликация по номеру аренды: повторная загрузка того же файла ничего не добавит
- **Счётчик номеров сдвигается за импортированные**, иначе следующая новая аренда
  получила бы уже занятый номер
- Пишем строки напрямую, минуя `createRental`: он вешает инструмент в аренду и заводит
  событие «Создал» — для закрытых аренд это неверно и засоряет историю

Проверено на выгрузках заказчика: каталог — 191 позиция → 425 единиц, клиенты —
10 000 строк → 5 897 карточек, аренды — 3 085 строк за ~1 сек (2 без клиента пропущены;
заведено 661 клиент и 350 единиц каталога, все 4 623 позиции связаны с карточками).

#### Цвет карточки = состояние аренды
Карточка в списке аренд разделена на цветную шапку и белый низ: статус должен
читаться с двух метров, не вчитываясь в подпись. Цвета в `statusHeaderStyles`
(`utils.ts`):

| Статус | Цвет |
|---|---|
| Запрос | серо-синий `#64748B` |
| Забронировано | синий `#2B5FD9` |
| В аренде | янтарный `#F5A623` |
| Завершено | зелёный `#2E9E5B` |
| Просрочено | пурпурный `#C13DD6` |
| Украдено | тёмно-красный `#8B1A1A` |
| Отменено | серый `#9AA0B4` |

**Долг перекрашивает шапку в `#F0522B` и меняет подпись на «Должник»** — но только у
**закрытых** аренд (`completed`/`stolen`): инструмент вернули, а деньги нет. Пока аренда
идёт, долга ещё нет — есть неоплаченный остаток, и он виден отдельной строкой, иначе
краснела бы каждая свежая невыплаченная аренда.

#### Массовое удаление
Чтобы разом убрать наигранные тестовые записи, в списках аренд и клиентов есть выбор:

- **Удалять пачкой может только администратор.** Кнопка «Выбрать» и чекбоксы видны
  лишь ему, и оба роута отвечают 403 всем остальным — даже с правом `rentals.edit`:
  обычный менеджер мог бы стереть половину базы одним нажатием
- **Каталог** — чекбоксы в таблице продуктов. Отмечается продукт целиком, за строкой
  стоят все его единицы. Инструмент **в идущей аренде** и **с заявкой в мастерской**
  пропускается: в отчёте видно, сколько и почему
- **Аренды** — кнопка «Выбрать» в шапке включает режим: клик по карточке отмечает её,
  а не открывает. Снизу всплывает плашка «Выбрано N · Выбрать все · Снять выделение · Удалить»
- **Клиенты** — чекбоксы в таблице всегда на месте, в шапке столбца — «выбрать всех»
- Подтверждение — своя модалка, а не `confirm()`: она перечисляет последствия
  (уйдёт история аренды, инвентарь освободится) и не мельчит на телефоне
- **Клиент с арендами по умолчанию не удаляется.** В модалке есть переключатель
  «Удалить вместе с арендами»; без него такие клиенты возвращаются в ответе как
  `skipped`, и в списке пишется, сколько пропущено и почему
- Роуты: `POST /api/rentals/bulk-delete` и `POST /api/clients/bulk-delete` (POST, а не
  DELETE: тело у DELETE поддерживают не все прокси). Права — `rentals.edit` / `clients.edit`,
  до 500 записей за раз, всё в одной транзакции
- Одиночное удаление клиента с арендами теперь отвечает **409 с объяснением**, а не
  «500 Внутренняя ошибка» от внешнего ключа

### Магазин (`/shop`)
Товары, которые продаются **безвозвратно** — перчатки, диски, смесь. С каталогом аренды
не связаны ничем: своя таблица `shop_products`, свои инвентарный и серийный номера,
свой остаток. В аренду такие позиции не выдаются и не возвращаются.

- Инвентарный номер уникален и присваивается сам (`МГ-1`, `МГ-2`…), если поле оставили
  пустым; серийный номер тоже проверяется на дубли — оба дают 409 с внятным текстом
- Карточка: название, категория, цена продажи, себестоимость (для наценки), остаток, заметка
- В шапке: позиций, штук на складе, товара на сумму, сколько закончилось
- Права: `shop.view` / `shop.edit`

**Продажа идёт через аренду.** В форме новой аренды появилась вкладка «Магазин»:
менеджер выбирает товар, указывает цену и количество (не больше остатка).

- Сумма такой строки **не умножается на срок аренды**: перчатки за неделю стоят столько же,
  сколько за день. За это отвечает `isOneTimeLine()` / `lineTotal()` в `src/lib/utils.ts` —
  ими же считаются услуги
- Остаток списывается **один раз, в момент выдачи** (переход аренды в `active`). Флаг
  `rentals.shop_written_off` страхует от повторного списания при правках; отмена аренды
  возвращает товар на склад
- В модалке возврата товаров магазина нет — они проданы

### Клиенты (`/clients`)
CRUD, поиск/фильтры, сортировка, статистика, импорт/экспорт CSV и Excel.
Бейдж «В чёрном списке» в шапке карточки.

**Блок «Документ клиента» зависит от типа клиента** — и в форме `/clients/new`, и в быстрой
модалке из формы аренды:

| Физ. лицо | Юр. лицо |
|---|---|
| ИИН, дата рождения, номер документа, кем выдан, даты выдачи/истечения | БИН, юридический адрес (офис), руководитель компании, ИИК (номер счёта), банк, БИК |

На карточке клиента для юр. лица вместо блока «Документ» показывается блок «Реквизиты».
Переменные шаблонов `{{client_bin}}`, `{{client_address}}`, `{{client_director}}`,
`{{client_account}}`, `{{client_bank}}`, `{{client_bik}}` берут реальные значения
(раньше были заглушками: БИН подставлялся из ИИН, руководитель — из названия, остальные пустые).
Реквизиты добавлены в импорт/экспорт клиентов.

**Рейтинг 1–5 звёзд считается сам** — вручную его больше не выставляют (поле из формы убрано,
колонка `clients.rating` осталась от старой ручной версии и не читается). Складывается из трёх
долей, `computeClientRating()` в `repo.ts`:

| Что | Вес | Как считается |
|---|---|---|
| Как часто обращается | 30 % | ступени 1 / 2 / 3 / 5 / 10 аренд |
| Платит | 35 % | доля аренд, закрытых полностью |
| Возвращает в срок | 35 % | доля аренд, отданных не позже `end_at` |

- Черновики и отменённые аренды в расчёт не идут
- Чёрный список или кража — сразу 1 звезда, статистика не спасает
- Без единой аренды рейтинга нет («—»): вешать новичку единицу нечестно
- Опоздание определяется по `rentals.returned_at` — дате фактического возврата. Она ставится
  при завершении аренды и снимается при откате, чтобы рейтинг не врал
- На карточке клиента под звёздами — три полоски с расшифровкой, чтобы рейтинг не был магией

### Мастерская (`/workshop`)
**Профилактику убрали из выбора при возврате** — её делают всем и всегда, отдельная
галочка только мешала. Приёмщик решает одно: инструмент **в строй**, **на
диагностику** или **сразу в ремонт**.

Доска заявок: **Новая → На обслуживании / В ремонте → Готово → Архив**. Обслуживание
и ремонт — параллельные ветки, а не этапы одной: инструмент либо на плановом ТО, либо
чинится. Для каталога оба состояния значат одно — инструмент временно не выдаётся.

Заявка с причиной «Диагностика» или «Обслуживание» показывает две кнопки итога:

- **«Исправен, в строй»** — заявка закрывается, инструмент возвращается свободным
- **«Нужен ремонт»** — та же заявка меняет причину на «Ремонт» и уходит в работу.
  Вторую заявку по тому же инструменту не заводим: история должна быть одной ниткой

Статус инвентаря выставляет сам репозиторий по причине и статусу заявки —
в интерфейсе его руками не трогаем, иначе получаются гонки.
Канбан: **Новая → В работе → Готово → Архив**, перетаскивание карточек.
Заявки создаются вручную или автоматически при возврате товара с профилактикой/ремонтом.
Запчасти и услуги с автоподсчётом. Аналитика поломок.
При переводе в «Готово» товар возвращается в `available`.

### Документы (`/documents`)
Раздел из двух вкладок: **«Созданные документы»** — реестр всего, что напечатали,
и **«Шаблоны»** — из чего это делают.

**Реестр**: документ, статус подписи, дата и способ подписания, кто отметил, клиент,
ссылка на аренду. Фильтры «Все / Подписано / Ожидает подписания», поиск по названию,
клиенту, телефону и номеру аренды. Тело документа в списке не тянется — на тысячах
строк это мегабайты HTML; оно читается при открытии.

**Подпись отмечается сразу после печати**: из карточки аренды документ печатается и тут
же спрашивается «Документ подписан?» с ответами «Да» и «Нет». Если ответили «нет» —
документ остаётся в реестре во вкладке «Ожидает подписания», и подписать его можно
оттуда кнопкой. Отметку можно и снять: печатают и ошибаются.

**Заготовка «Акт приёма-передачи»** повторяет рабочую форму проката: рамка с номером,
город и дата, преамбула сторон, таблица оборудования на шесть колонок, восемь пунктов и
подписи с реквизитами. Всё, что меняется от аренды к аренде, вписано переменными —
остальное правится в редакторе. Заготовки живут в `lib/document-blueprints.ts`.

**Шрифт, размер и цвет** — три селекта в тулбаре. Размеры в пунктах (8–24 пт), как
принято в документах. Если ничего не выделено, стиль применяется **ко всему шаблону**:
чаще всего нужно именно «сделать во всём документе 12 пт».

**Редактор показывает разбивку на листы.** Раньше лист просто тянулся вниз: шаблон
выглядел одностраничным, а на печати подписи уезжали на второй лист. Теперь под шапкой
написано «Помещается на один лист» или «Займёт листов: N», а по документу проходит
красная пунктирная линия «конец листа».

**Страницы считаются по блокам, а не по общей высоте.** Таблицы и заголовки не рвутся
между листами, поэтому блок, не влезающий в остаток страницы, уезжает на следующий
целиком — из-за этого акт, который по сумме высот помещался, печатался на двух листах
с полупустым первым. Подсчёт это учитывает, и масштаб подбирается шагами, пока документ
не уложится в один лист (с запасом 3 %).

**Печать подгоняет документ под страницу.** По ширине — чтобы не срезало правый край
таблицы; по высоте — если акт не помещается «на пару строк», он ужимается до одного
листа. Ниже 72 % не опускаемся: дальше подписи не разобрать, и честный перенос лучше.
Документ, который занимает две полные страницы и больше, не ужимается вовсе.

Поля печати и редактора сведены к одним 10 мм, межстрочный интервал — к 1,5: пока они
расходились, высота на экране и на бумаге не совпадала.

**Лист в редакторе — ровно A4** (210×297 мм) с теми же полями 12 мм, что при печати:
что видно в редакторе, то и ляжет на бумагу. Внутренний отступ редактора убран —
раньше поля удваивались, и текст не помещался по ширине.

**Печать идёт из скрытого iframe, а не из нового окна.** Раньше `window.open` уводил
на пустую страницу, в колонтитул попадал `about:blank`, а блокировщик всплывающих
окон мог вообще не дать напечатать. Перед печатью документ **подгоняется по ширине**:
если он шире печатного поля A4, масштаб уменьшается (но не ниже 65 %) — без этого
правый край таблицы просто обрезался.

В редакторе шаблонов: **готовые заготовки** (акт приёма-передачи, договор аренды,
расписка), **поиск по переменным** и кнопка **«Печать»** — посмотреть, как ляжет на
лист, не выходя из редактора.
**WYSIWYG-редактор на TipTap:**
- Визуальный лист А4, тулбар (жирный/курсив/подчёркнутый, выравнивание, списки, таблицы)
- **Импорт Word** (.docx) через mammoth
- Правая панель с **80+ переменными**: Компания / Общее / Аренда / Клиент / Продукты
- Вставка переменной в позицию курсора по кнопке `+`

**В карточке аренды** — блок «Документы»: выбор шаблона → генерация с подстановкой
данных → просмотр, печать, удаление.

**Стили готового документа — `src/lib/document-styles.ts`, один набор на предпросмотр
и на печать.** Раньше окно печати открывалось вообще без CSS: рамки таблиц рисовало
правило `.ProseMirror table` из `globals.css`, которое в новом окне не действует.
Из-за этого таблицы теряли границы и заливку, а браузерный Times 16px раздувал документ
на лишнюю страницу.

- `DOCUMENT_CSS` повторяет правила редактора (таблицы, заголовки, списки, размер шрифта)
- `DOCUMENT_PRINT_CSS` добавляет `@page { size: A4; margin: 14mm 12mm }`,
  запрет разрыва строк таблицы и **`print-color-adjust: exact`** — без него браузер
  выбрасывает заливку ячеек и цветной текст при печати
- предпросмотр показывает документ листом А4 с теми же полями, что и печать
- лист в редакторе тоже получил поля `14mm`, чтобы переносы строк в шаблоне и в готовом
  документе совпадали

Меняете вид таблиц — правьте `DOCUMENT_CSS` и `.ProseMirror` в `globals.css` вместе,
иначе редактор и печать разъедутся.

Суммы «текстом» (`{{total_text}}` → «шесть тысяч тенге») для договоров.

### Воронка (`/funnel`) — заявки

Доска входящих заявок: клиент позвонил, менеджер завёл карточку и указал, **когда клиенту
нужен инструмент**. Пункт меню стоит под «Клиентами».

**Колонки:** Клиенты на сегодня · Нужно на завтра · Нужно на этой неделе ·
Нужно в будущем · Нет в наличии.

**Главное решение: колонка НЕ хранится в базе.** Она вычисляется из `needed_at` функцией
`leadBucket()` в `src/lib/funnel.ts`. Поэтому заявка «на завтра» сама оказывается
в «сегодня», когда наступает завтра, — и это работает без фонового задания, которое
может не отработать или сдвинуть все карточки, если сервер простоял ночь выключенным.
Проверено на границе полуночи: 6 сентября 23:59 — «завтра», 7 сентября 00:01 — «сегодня».

- **Просроченные не теряются:** вчерашние и более старые тоже попадают в «сегодня»,
  дата на карточке краснеет
- «Нет в наличии» — ручной флаг `unavailable`, он сильнее даты: галочка
  «Инструмента нет в наличии» в форме кладёт карточку в эту колонку независимо
  от того, что стоит в дате
- Страница пересчитывает колонки **раз в минуту** (`setInterval`), чтобы вкладка,
  открытая со вчера, не показывала вчерашнюю картину
- Перетаскивание карточки в другую колонку **меняет дату** (`dateForBucket()`),
  а не какой-то отдельный статус. На телефоне вместо перетаскивания — выпадающий список

**Закрытие сделки:** пока карточку тащат, внизу появляются две полосы —
«Успешно завершено» и «Не реализовано». Статус `status`: `open` / `won` / `lost`.
Закрытые уходят с доски на отдельные вкладки — иначе через полгода в браузер
уезжали бы тысячи мёртвых карточек.

**Права:** `leads.view` — просмотр, `leads.edit` — создание и изменение.

**Фильтры:** поиск (инструмент, клиент, телефон, номер — с задержкой 300 мс, чтобы
не дёргать сервер на каждую букву), менеджер, канал привлечения. Фильтрация и итоги
в шапке считаются в SQL.

Нумерация заявок сквозная (`№1, №2…`), как в референсе.

#### Форма заявки
Собрана по макету заказчика: инструмент (подсказки из каталога), клиент, телефон,
сумма, менеджер, откуда пришёл, тип клиента, дата и время, две галочки —
«Инструмента нет в наличии» и «Другой город», блок «Что смущает клиента»
(дорого / далеко / дорогая доставка), комментарий и настроение клиента пятью лицами.

- **Дата обязательна, и это главное правило формы.** Поле пустое и горит красным,
  «Сохранить» не нажимается, пока менеджер не спросит у клиента дату и время.
  Раньше дата подставлялась сегодняшним числом — вся воронка забивалась карточками
  «на сегодня», и колонки переставали что-либо значить
- Правило снимается галочками «нет в наличии» и «другой город»: спрашивать дату
  не с чего. Проверка продублирована на сервере (`POST /api/leads`)
- Телефон форматируется при вводе (`+7 (707) 123-45-67`). Код страны отрезается
  только у полного номера — иначе набранное «707…» превращалось в «07…»
- Настроение и возражения видны прямо на карточке доски, вместе с именем клиента
  и временем: менеджеру не нужно открывать заявку, чтобы понять, о чём разговор

**Заявка → аренда одной кнопкой.** В карточке заявки кнопка «Оформить аренду»
(нужно право `rentals.edit`):

1. `POST /api/leads/[id]/convert` ищет клиента **по телефону без учёта форматирования**
   (`+7 707 370-51-31` и `87073705131` — один человек, сравниваются последние 10 цифр).
   Нашёлся — берём его, нет — заводим нового с каналом привлечения из заявки.
   Повторное нажатие дубля не создаёт.
2. Открывается обычная форма аренды `/rentals/new?client=…&lead=…&title=…&needed=…`
   с подставленным клиентом и датой начала из заявки, сверху — плашка с тем,
   что клиенту нужно.
3. После «Забронировать аренду» заявка автоматически закрывается как успешная.

Саму аренду эндпоинт не создаёт намеренно: инструмент, сроки, залог и оплату собирает
менеджер в существующей форме, дублировать эту логику ради одной кнопки незачем.

Параметры в форме аренды читаются из `window.location.search`, а не через
`useSearchParams` — тот требует обёртки в `Suspense` и ломает пререндер страницы.

### Темп (`/tasks`) — задачи сотрудников и KPI

Доска в духе Trello: колонки **Новая → В работе → На проверке → Выполнена → Отменена**,
перетаскивание карточек мышью, на телефоне статус меняется выпадающим списком.
Пункт меню стоит над «Настройками».

**Права:**

| Право | Что даёт |
|---|---|
| `tasks.view` | Свои задачи: где сотрудник исполнитель или постановщик, плюс те, что ему открыли |
| `tasks.manage` | Все задачи, постановка, назначение исполнителя, сроки, вес, удаление и KPI по всем |

**Видимость задачи** — исполнитель, постановщик и те, кого явно отметили в блоке
«Кому ещё видна задача». Список зрителей лежит в отдельной таблице `task_viewers`
(а не JSON-полем), чтобы выборка шла по индексу.

**Ограничения на изменение** (`PATCH /api/tasks/[id]`): с `tasks.manage` меняется всё;
исполнителю разрешён только собственный статус — сроки, вес и список зрителей он не
подкрутит. Проверка серверная, не в интерфейсе.

**KPI** — вкладка рядом с доской, периоды 7 / 30 / 90 дней и всё время:

- баллы: вес выполненных задач (задаётся при постановке, рутина 1, крупная 3–5)
- в срок и с опозданием, среднее время выполнения
- сводная оценка 0–100: **60% — доля закрытых задач, 40% — доля закрытых в срок**;
  задачи без срока считаются выполненными вовремя

Момент выполнения фиксируется в `done_at` при переводе в «Выполнена» и **сбрасывается**
при возврате в работу — иначе KPI можно было бы накрутить перекладыванием карточки.

**Что сделано ради нагрузки** (раздел добавлялся с оглядкой на то, что функций уже много):

- задачи **не входят** в общий `store.hydrate()` — он тянется на каждой странице,
  а «Темп» нужен не всем. Страница грузит свои данные сама
- фильтр видимости стоит в SQL, а не на клиенте: чужие задачи не уезжают в браузер даже в ответе
- KPI считается одним агрегатом в SQLite, а не переносом всех задач в JS
- индексы `idx_tasks_assignee`, `idx_tasks_status`, `idx_tasks_done_at`, `idx_task_viewers_user`;
  выборка «мои задачи» идёт по индексу (проверено `EXPLAIN QUERY PLAN`)
- список задач ограничен 300 записями на запрос
- список сотрудников отдаёт общий лёгкий `/api/staff` (id, имя, должность), а не
  `/api/users` с правами и хешами. Им пользуются и «Темп», и «Воронка»
- перенос карточки применяется оптимистично и откатывается, если сервер отказал

### Доставка (`/delivery`)

Раздел перестал быть заглушкой. Доставка рождается из аренды: в её карточке блок
«Доставка» с плюсом, оттуда открывается та же модалка, что и в разделе.

**Стадии** — вкладки со счётчиками: Новые запросы → В процессе → Завершено (+ Отменённые).
Кнопка «Доставить» переводит запрос в работу и **назначает нажавшего курьером**, если
исполнитель не выбран заранее; «Завершить» закрывает. Отметки `started_at` и
`completed_at` ставятся один раз и сбрасываются при откате статуса — по ним считается
реальное время в пути.

**Просрочка живая.** Срок `deliver_by` сравнивается с текущим временем прямо на карточке:
красный бейдж «Просрочено» и отсчёт «Уже просрочено на 4 д. 3 ч. 55 мин.». За два часа до
срока появляется жёлтое «Скоро срок». Страница пересчитывает время раз в минуту, поэтому
вкладка, открытая с утра, не показывает утреннюю картину.

**Что везём — позиции самой аренды.** Список не дублируется в таблице доставок, а
подтягивается из `rentals.items_json` при чтении: иначе состав доставки разъезжался бы
с составом аренды после её правки.

**Поля модалки:** Доставка или Вывоз (вывоз меняет смысл адресов местами), исполнитель,
срок, адрес выдачи и адрес доставки, номер клиента и номер получателя (когда принимает
другой человек), цена, маршрут (ТУДА / ОБРАТНО / ТУДА ОБРАТНО), комментарий.
Из карточки аренды телефон клиента и пункт проката подставляются сами.

**Аналитика** — кнопка в шапке: всего, выполнено, в пути, просрочено, заработано,
среднее время в пути и разбивка по курьерам. Считается в SQL одним набором запросов.

**Права:** `delivery.view` — просмотр, `delivery.edit` — создание и выполнение.
Смена стадий и правка доставки отражаются в истории аренды.

Номера доставок сквозные (`delivery_counter` в `company_settings`), как у аренд и заявок мастерской.

### Настройки (`/settings`)
Данные компании: название, БИН, город, адрес, руководитель, валюта, телефон, email,
банк, БИК, счёт, логотип. Подставляются в шаблоны через `{{company_*}}`.
Редактирует только главный администратор.

### Аналитика

#### Кто заплатил, а кто нет
Под поступлениями — поимённый список за тот же период (`/api/analytics/payers`,
`paymentsLedger()`). На «24 часах» это ровно сегодняшняя касса и сегодняшние долги.

- **Оплатили:** клиент с телефоном, номер аренды, способ, время и кто принял деньги
- **Не оплатили:** аренда с остатком — сколько внесено, сколько должен, до какого срока
- Должники ищутся и по дате оформления, и по дате окончания аренды: за сутки попадают
  и те, кто взял инструмент сегодня, и те, кто сегодня должен вернуть
- Сводка считает клиентов, вкладки — аренды: у одного человека может быть два долга (`/analytics`)
**Блок «Поступления за период»** — два разреза одних и тех же денег, переключаются
кнопками «Все / Чем платили / За что»:

| Чем платили | За что |
|---|---|
| Kaspi, наличные, от компаний | аренда инструмента, магазин, доставка |

- Способ оплаты берётся из таблицы `rental_payments`: раньше модалка его спрашивала,
  а сохранялась только сумма — разложить кассу было не по чему
- Оплаты, принятые до появления этой таблицы, показываются отдельной строкой:
  они входят в общую сумму, но по способам не разложены
- «Магазин» — стоимость проданных товаров внутри аренд, «Доставка» — выполненные
  доставки. Складывать разрезы между собой не нужно, и в интерфейсе это написано
Периоды: **24 часа** / 7 дней / 30 дней / 12 месяцев / Всё время **плюс кнопка «Выбрать даты»**
для произвольного диапазона.
6 KPI + график выручки (столбцы) + количество аренд (линия) + пирог по статусам +
топ-10 клиентов + топ-10 инвентаря с прогресс-барами.

## 3.1 Мобильная версия

Приложение адаптировано под телефон 9:16 (проверялось на 375×812).

**Ключевое правило: на компьютере интерфейс остаётся прежним при любой ширине окна.**
Мобильная раскладка включается по УСТРОЙСТВУ, а не по ширине — сузили окно браузера
на десктопе, интерфейс не меняется.

**Как определяется телефон** — `src/lib/use-is-mobile.ts`, хук `useIsMobile()`:
- user-agent телефона/планшета, **или**
- iPadOS 13+ (представляется Mac'ом — ловим по `maxTouchPoints > 1`), **или**
- `pointer: coarse` И при этом `any-pointer: fine` отсутствует, то есть мыши в системе нет
  (ноутбук с сенсорным экраном сюда НЕ попадает — у него есть точный указатель)

До монтирования возвращает `false` — иначе разъезжается гидратация.

На хук завязаны все перестроения раскладки: выдвижное меню, стопка колонок в карточке
аренды, в форме новой аренды, в редакторе документов и в шапке каталога.
Медиа-запрос мобильных стилей в `globals.css` тоже сужен до `(pointer: coarse)`.

**Оболочка** (`app-shell.tsx`):
- на телефоне боковая панель превращается в выдвижное меню (`Sidebar mobile open onClose`)
  с затемнением; закрывается по тапу на фон, по крестику и при переходе по ссылке
- вместо неё сверху — `MobileTopBar`: бургер, логотип, кнопка «+» на новую аренду
- под открытым меню body не прокручивается
- высота везде `100dvh`, а не `100vh` — иначе адресная строка мобильного браузера обрезает низ

**Что сделано по разметке:**
- `export const viewport` в `layout.tsx` — без него мобильный браузер рендерит страницу
  в ширине 980px и ужимает её; там же `viewportFit: "cover"` и `themeColor`
- утилиты `.safe-top` / `.safe-bottom` под чёлку и домашнюю полосу iOS
- **поля ввода на телефоне 16px** — при меньшем размере iOS зумит страницу на фокусе
- двухколоночные формы (клиент, инвентарь, комплект, настройки, пользователи) —
  в один столбец до `sm`
- двухколоночные экраны (карточка аренды, форма новой аренды, редактор документов) —
  стопкой **на телефоне** (через `useIsMobile()`, не через брейкпоинт), боковые панели
  во всю ширину вместо `w-[340px]`
- модалки на телефоне приезжают снизу на всю ширину со скруглением только сверху,
  высота `92dvh`, прокрутка внутри
- вкладки каталога и переключатели периодов не переносятся, а прокручиваются по горизонтали;
  кнопки действий уходят на строку ниже **только на телефоне**
- фильтры каталога на телефоне — сетка 2×N вместо ряда
- таблицы прокручиваются горизонтально внутри карточки (`TableCard`)
- hover-эффекты отключены при `(hover: none)` — на тапе они залипали

## 3.2 Периоды в аналитике и финансах

Общий переключатель — `src/components/ui/period-picker.tsx`, общая логика — `src/lib/period.ts`.
Обе страницы используют одно и то же, чтобы не разъезжались.

- Быстрые кнопки: `day` (24 часа), `week`, `month`, `year`, `all`
- Кнопка «Выбрать даты» открывает два поля и кнопку «Применить»; выбранный диапазон
  показывается прямо на кнопке (`01.09.2026 — 06.09.2026`)

**Границы диапазона считает браузер, а не сервер.** Пользователь выбирает даты в своём
часовом поясе, а `created_at` в базе лежит в UTC: клиент превращает `2026-09-01` в
`2026-09-01T00:00:00` по местному времени и отправляет готовый ISO. Сервер их только проверяет.

**Шаг графика (`granularity`) выбирает сервер** и возвращает вместе с данными:

| Период | Шаг |
|---|---|
| 24 часа, свой диапазон до 2 суток | по часам |
| 7 и 30 дней, свой диапазон до 92 дней | по дням |
| 12 месяцев, всё время, свой диапазон длиннее 92 дней | по месяцам |

Без этого сутки рисовались бы одним столбцом, а год — тремя сотнями.

**Важно при доработке запросов:** у всех выборок с периодом теперь ДВЕ границы —
`created_at >= ? AND created_at <= ?`. Раньше была только нижняя, и произвольный
диапазон молча захватывал всё до сегодняшнего дня. Добавляете новую метрику за период —
не забудьте верхнюю границу.

## 3.3 Доступ к API — правила, которые нельзя нарушать

**Каждый роут обязан вызывать `requireAuth(<право>)`.** Middleware проверяет только
наличие cookie, но не её подлинность — с подставленным `rental_crm_session=что угодно`
раньше открывались клиенты, инвентарь, аренды и шаблоны, и создавались записи.
Единственная настоящая защита — проверка в самом роуте.

| Раздел | Чтение | Запись |
|---|---|---|
| Клиенты | `clients.view` | `clients.edit` |
| Каталог, комплекты, услуги, инвентаризация | `catalog.view` | `catalog.edit` |
| Аренды, документы аренды | `rentals.view` | `rentals.edit` |
| Мастерская | `workshop.view` | `workshop.edit` |
| Шаблоны документов | `documents.view` | `documents.edit` |
| Воронка | `leads.view` | `leads.edit` |
| Темп | `tasks.view` | `tasks.manage` |
| Аналитика / Финансы | `analytics.view` / `finance.view` | — |
| Магазин | `shop.view` | `shop.edit` |
| Массовое удаление аренд и клиентов | — | только администратор (без ограничения по количеству) |
| Импорт каталога, клиентов и аренд | — | только главный администратор |
| Пользователи | `users.view` | `users.edit` |
| Лента, загрузка и отдача файлов, справочник сотрудников | любой вошедший | — |

- `/api/file/[name]` тоже под авторизацией: там фото клиентов и сканы документов.
  Локально файлы дополнительно лежат в `public/uploads` и раздаются статикой — на
  боевом сервере задавайте `UPLOADS_DIR`, чтобы они шли только через роут
- `/api/cron` — единственное исключение: он ничего не отдаёт, только пересчитывает
  просрочки. Задайте `CRON_SECRET`, и он начнёт требовать заголовок `x-cron-secret`
- **Главного администратора нельзя ни удалить, ни заблокировать, ни разжаловать** —
  проверка в `repo.ts`, не в интерфейсе. Раньше запрет был только в UI, и через API
  систему можно было запереть
- **Роль администратора выдаёт только владелец**: `POST /api/users` и
  `PATCH /api/users/[id]` отвечают 403 на `isAdmin`, если запрос пришёл не от него.
  Иначе любой сотрудник с `users.edit` поднял бы себе полный доступ
- **Сессия не источник истины**: роль и права читаются из базы на каждом запросе.
  Цена — один индексный SELECT, зато выдача роли и блокировка действуют мгновенно

**Валидация — тоже на сервере.** Хелперы в `auth.ts`: `required()`,
`nonNegative()`, `assertNonNegativeFields()`. Формы блокируют кнопку, но API обязан
проверять сам: до этого проходили клиент без имени, товар без названия, цена −500 ₸
и оплата −9999 ₸, которая тут же ломала аналитику.

**Ошибки отдаются через `apiError(e)`** — она понимает `status` у ошибки. Бросайте из
репозитория `httpError(409, "…")`, и пользователь увидит текст, а не «500».

## 5.1 Что было исправлено по итогам сплошной проверки

Разовая ревизия всех функций (сентябрь 2026) нашла и закрыла:

- **Доступ без пароля** — 23 роута не проверяли сессию (см. 3.3)
- **Файлы клиентов раздавались всем** — `/api/file` без авторизации
- **Главного администратора можно было заблокировать через API**
- **Аналитика и финансы не проверяли право на раздел**
- **Сумма прописью врала на всех суммах от 1000** — «четыре тенге тысяч(и) пятьсот
  тенге» вместо «четыре тысячи пятьсот тенге». Функция звала саму себя, а сама же
  дописывала «тенге»; склонения были заглушками
- **Все финансовые операции падали на дату создания аренды** — теперь у оплаты есть
  `rentals.paid_at`, у штрафов и расходов — собственный `createdAt`
- **Тип расхода терялся** — в таблице всегда было «Расход по аренде №…»
- **Штрафы считались доходом в графике, но не в KPI** — теперь нигде: штраф это
  начисление, деньги приходят через оплату
- **Товар с заявкой в мастерской не удалялся с ошибкой 500** — теперь 409 с объяснением
- **Заявку мастерской нельзя было удалить** — добавлены DELETE и кнопка в карточке
- **Номера заявок мастерской были случайными** (`WS-770073`) — стали сквозными
- **«Ожидаемые возвраты» дублировали «Активные аренды»** — теперь это возвраты на сегодня
- **«Выручка за сегодня» считалась по дате начала аренды** — теперь по дате оплаты
- **Топ инвентаря двоился** — ключ был `inventoryItemId ?? name`, стал по названию
- **«Активные аренды» значили разное** на главной и в аналитике — везде только `active`,
  брони показываются отдельной строкой
- **Имя проверяющего в инвентаризации приходило из тела запроса** — берётся из сессии

## 5.2 Что делать, когда данных стало много

После импорта боевой базы (3 000 аренд, 6 500 клиентов, 780 единиц) приложение
заметно поехало. Разобрали по причинам:

| Что было | Почему | Стало |
|---|---|---|
| `/api/rentals` — 1150 мс | На каждую аренду отдельный `getClient()`, а тот ещё считал статистику и рейтинг клиента | 154 мс: клиенты поднимаются пачкой и раздаются по ссылке |
| `/api/clients` — 1612 мс | На каждого клиента отдельный SELECT его аренд | 85 мс: один проход по таблице аренд, сгруппированный по клиенту |
| 6,3 МБ на каждую загрузку | Next сжимает только страницы, ответы route handlers уходят как есть | 663 КБ: тяжёлые списки отдаются gzip через `jsonCompressed()` |
| Браузер рисовал 3 000 карточек | Список рендерился целиком | 60 карточек и кнопка «Показать ещё»; у клиентов — 100 строк. Поиск и фильтры при этом работают по всей базе |

**Правила на будущее:**

- Никогда не звать `getClient()` в цикле — он считает статистику и рейтинг по всем
  арендам клиента. Для списков есть `rentalSummariesByClient()`
- Тяжёлые списки отдавать через `jsonCompressed(req, data)` из `lib/api-response.ts`:
  `compress: true` в `next.config.ts` на route handlers **не действует**
- Любой список, который может вырасти до тысяч строк, рисовать порциями

## 6. Грабли (не наступать снова)

1. **`secure: true` на cookie ломает сессию на Railway.** Reverse proxy: браузер видит
   HTTPS, внутри HTTP → куки не передавались, выкидывало на логин. В `src/lib/session.ts`
   стоит `secure: false`.

2. **`tsconfig.tsbuildinfo` ломает Docker-сборку** (`not a directory`). Убрали
   `"incremental": true` из `tsconfig.json`, файл в `.gitignore`.

3. **`healthcheckPath` должен быть `/login`.** На `/` и `/api/auth/me` — Healthcheck failure.

4. **В таблице `rentals` НЕТ колонки `client_json`.** Клиент через `client_id`.
   Из-за `r.client_json` крашились `/api/analytics` и `/api/finance`.
   Используйте `JOIN clients c ON c.id = r.client_id`.

5. **`serverExternalPackages: ["better-sqlite3", "bcryptjs"]`** в `next.config.ts` обязателен.

6. **`src/instrumentation.ts` ломает сборку** если импортирует better-sqlite3.
   Планировщик запускается при импорте `repo.ts` с защитой `global.__penaltySchedulerStarted`.

7. **Next.js 15:** `params` — это `Promise`, нужен `await params`
   (или `use(params)` в клиентских компонентах).

8. **Новые колонки в существующих таблицах — только через `ensureColumns()` в `db.ts`.**
   `CREATE TABLE IF NOT EXISTS` не меняет структуру уже созданной таблицы, поэтому на боевой
   базе новое поле появится только через `ALTER TABLE ADD COLUMN`. Хелпер сверяется с
   `PRAGMA table_info` и **глотает ошибку `duplicate column name`**: воркеры сборки Next
   импортируют модуль параллельно и без этого первый деплой падает.

9. **Вся схема создаётся одним `db.exec`.** При сборке Next поднимает несколько воркеров,
   каждый импортирует `db.ts`; если разбить DDL на два вызова, первый прогон на пустой базе
   падает с `SQLITE_BUSY: database is locked`. Новые таблицы добавлять внутрь существующего
   блока, а не отдельным `db.exec`.

10. **Даты аренды хранятся только в `start_at`/`end_at`.** Поля `startDate`/`endDate`
    в домене — производные (`.slice(0, 10)` от ISO), их заполняет `rentalRowToDomain`.
    Раньше они возвращались пустыми строками: в карточке и в списке аренд даты не
    отображались, а «Выручка за сегодня» на главной (фильтр `startDate.startsWith(today)`)
    всегда показывала 0. Для показа пользователю берите `formatDateTimeDisplay(startAt)`,
    для сравнения по дню — `startDate`.

11. **Мобильную раскладку включать по устройству, а не по `max-width`.** Первая версия
    адаптива ориентировалась на ширину окна — и на компьютере с узким окном пользователь
    получал мобильный интерфейс, чего быть не должно. Новые мобильные правила вешать
    на `useIsMobile()` или на `(pointer: coarse)`, а не на голый брейкпоинт.

12. **`useIsMobile()` до монтирования обязан возвращать `false`.** Сервер не знает ширину
    окна: если хук сразу вернёт `true`, серверная и клиентская разметка разойдутся и React
    выбросит hydration error.

13. **Не запускать `npm run build` при работающем `npm run dev`.** Продакшен-сборка
    перезаписывает `.next`, дев-сервер начинает отдавать `Internal Server Error`
    (`Cannot find module './xxxx.js'`). Лечится: остановить dev, `rm -rf .next`, запустить заново.

14. **Hydration error от расширений браузера** (`bis_register`) — решено через
   `suppressHydrationWarning` на `<html>`/`<body>` + флаг `mounted` в `AppShell`.

15. **Роль и права нельзя брать из cookie.** Сессия — снимок на момент входа: пока
   человек не перезайдёт, выданная роль администратора не работала бы, а
   заблокированный продолжал бы ходить по системе. `getCurrentUser()` перечитывает
   пользователя из базы на каждом запросе.

17. **Цена позиции не всегда умножается на срок.** Услуга — разовая работа, товар магазина
   продаётся насовсем. Для сумм по строкам аренды берите `lineTotal()` / `isOneTimeLine()`
   из `utils.ts`, а не `pricePerDay * qty * days`: иначе перчатки за неделю подорожают
   в семь раз.

19. **На аренду ссылаются мастерская и доставка.** `workshop_tickets.source_rental_id` —
   настоящий внешний ключ, и без снятия ссылки удаление падало с «FOREIGN KEY constraint
   failed», откатывая всю пачку. Заявку и доставку при этом удалять нельзя: ремонт и
   поездка курьера — отдельная работа, у них своя история. В `deleteRental()` ссылки
   обнуляются, а сами записи остаются.

18. **Сид администратора выполняется ПОСЛЕ блока миграций.** Бэкфилл `is_owner`
   отрабатывает при загрузке `db.ts`, когда таблица пользователей ещё пуста, поэтому
   на свежей установке владельца назначать не из кого. Флаг ставится прямо во вставке
   админа — иначе на новом деплое никто не смог бы выдавать права администратора.

22. **`transform: scale()` не влияет на разбивку страниц.** Он только рисует
   уменьшенную картинку, а браузер режет документ по исходной вёрстке: акт оставался
   на двух листах, просто мелким шрифтом. Уменьшать надо через `zoom` — он меняет сам
   layout. Проверено замером: у контейнера с transform высота 968 px, с zoom 0.8 — 774.

21. **Нельзя мерить вёрстку в iframe нулевого размера.** Печатный кадр создавался
   размером 0×0, в нём вёрстка схлопывается — все замеры высоты врали, и подгонка
   под лист не срабатывала. Кадр должен быть размером с печатную страницу.

20. **`LOWER()` в SQLite не знает кириллицы.** Поиск «иванов» не находил запись
   «ИВАНОВ» — половина базы просто не находилась, а выглядело это как «поиск иногда
   не работает». В `db.ts` зарегистрирована своя функция `rulower()`, все поисковые
   запросы идут через неё.

16. **Миграция колонки применяется только при перезапуске сервера.** `ensureColumns`
   отрабатывает при загрузке `db.ts`. Добавили колонку — перезапустите `npm run dev`,
   иначе получите `no such column`.

## 7. Принципиальные решения

- **Никаких фейковых данных.** Дашборд стартует с нуля. `mock-data.ts` — только справочники.
- **Источник истины — SQLite на сервере.** Zustand — только кэш. Если что-то не отображается,
  проверить что `StoreHydrator` смонтирован.
- **Всё только из каталога.** Товары, комплекты и услуги выбираются из справочников,
  ручной ввод в форме аренды убран.
- **Продукт — это группа единиц по названию, а не отдельная сущность.** Поштучный учёт
  (аренда, мастерская, QR, возврат по состоянию) завязан на единицу и остаётся нетронутым.
- **Права проверяются и в UI, и в API.** Не использовать `if (user.role === "admin")`.
